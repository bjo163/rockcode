# M1.1 Contract Validation Closeout — Design

**Date:** 2026-11-02
**Milestone:** M1.1 (contract-validation tooling)
**Decision owner:** repository owner (bjo163)
**Status:** design approved in conversation; awaiting owner review of this document.

## 0. Problem statement

M1.1 is currently recorded as "implemented as a CI scaffold, awaiting execution
evidence" ([09-validation-status-and-audit-log.md](../../specs/m0/09-validation-status-and-audit-log.md) §5).
A green GitHub Actions run exists
([41437355103](https://github.com/bjo163/rockcode/actions/runs/41437355103),
head `67be36b`), but that green run does **not** constitute contract validation,
and the runner's documented promise of "one local/CI entry point"
([M1.1-contract-validation.md](../../specs/m0/M1.1-contract-validation.md) §What is installed)
is false on the owner's Windows workstation.

Closing M1.1 therefore means two separate claims, each needing its own evidence:

1. **The gate detects violations.** The runner must fail on bad contracts and pass
   on good ones, on both Linux CI and Windows local, for a *reason*.
2. **The current contracts are clean.** Validation must produce zero findings,
   not zero *errors* while tolerating findings the config demoted to warnings.

## 1. Measured current state

All of the following were measured on 2026-11-02 against `main` at `67be36b`.

### 1.1 The green run is green because the runner reads only the exit code

`redocly lint` exits **0** while reporting findings, so exit-code checking treats
findings as success. From the CI log of run 41437355103:

```
[contract-validation] OpenAPI lint (@redocly/cli@2.72.1)
contracts/openapi/v1/openapi.yaml: validated in 62ms
Woohoo! Your API description is valid. 🎉
You have 31 warnings.
[contract-validation] AsyncAPI lint (@redocly/cli@2.72.1)
contracts/asyncapi/v1/session-events.yaml: validated in 26ms
Woohoo! Your API description is valid. 🎉
[WARNING] Unused rules found in redocly.yaml: operation-2xx-response,
operation-summary, operation-4xx-response, info-license.
```

The runner's header comment asserts "A failed tool invocation is a failed
validation; the runner does not convert a failure into a warning or success"
([validate-contracts.mjs:17-48](../../../scripts/validate-contracts.mjs#L17),
[M1.1 §Checks performed](../../specs/m0/M1.1-contract-validation.md)). The
inverse is what actually happens: **warnings are converted into success.**

### 1.2 The 31 OpenAPI findings, exactly

From `redocly lint --format json` on `contracts/openapi/v1/openapi.yaml`:

| Rule | Count | Locations |
|---|---:|---|
| `tag-description` | 8 | `#/tags/0..7/description` (openapi.yaml:18-25) |
| `operation-4xx-response` | 23 | the `responses:` key of every operation except `connectSessionEvents` |

The 23 flagged `responses:` lines: 33, 46, 60, 74, 94, 121, 142, 164, 182, 192,
227, 248, 264, 288, 316, 341, 364, 380, 422, 444, 484, 520, 535.

There are **24** operations. `connectSessionEvents` (openapi.yaml:393) already
declares `'401': Unauthorized` and `'403': Forbidden`, so it is not flagged.

Authentication status was checked rather than assumed: root `security` is
`BearerAuth` (openapi.yaml:15-16) and only **two** operations override it with
`security: []` — `getLiveness` (line 32) and `getReadiness` (line 45). The other
22 are authenticated. (An earlier draft of this design claimed five
unauthenticated operations; that was wrong and is corrected here.)

### 1.3 The AsyncAPI finding is a config bug, not a contract rule

`[WARNING] Unused rules found in redocly.yaml` means the four rules declared at
the top level of `redocly.yaml` are **OAS rules that never apply to an AsyncAPI
document**. They are dead configuration, and Redocly says so on every AsyncAPI
lint. Fixing this is a config restructure, not an API-contract edit.

### 1.4 The runner is unusable on Windows

On a clean `git archive HEAD` checkout, `node scripts/validate-contracts.mjs`
fails **17 of 17** tool invocations with:

```
ERROR: OpenAPI lint (@redocly/cli@2.72.1): spawnSync npx.cmd EINVAL
```

Root cause: [validate-contracts.mjs:19](../../../scripts/validate-contracts.mjs#L19)
selects `npx.cmd` on `win32` and calls `spawnSync` **without** `shell: true`.
Node ≥ 18.20 / ≥ 20.12 / ≥ 21.7 refuses to spawn `.cmd` files that way
(CVE-2024-27980 hardening) and throws `EINVAL`. `result.error` is set, `fail()`
runs, and every check dies before invoking a validator.

**Retraction.** An earlier draft claimed a total local failure could leave the
gate green ("silent double failure → Node exits 0"). Measured: the local run
exits **1**. `fail()` sets `process.exitCode = 1` at
[validate-contracts.mjs:15](../../../scripts/validate-contracts.mjs#L15), so any
failure propagates. That hazard does not exist and the design does not need a
sentinel line to protect against it.

What the runner genuinely lacks is **aggregation and reporting**: `runNpx`
returns a boolean that all 17 call sites discard (lines 152-174), so it can print
concrete `ERROR:` lines but cannot emit a pass/fail count. That matters for the
evidence format in §3.4, not for red/green correctness.

### 1.5 `main` is not protected

`gh api repos/bjo163/rockcode/branches/main/protection` → 404 `Branch not
protected`. The acceptance criterion "The workflow runs on relevant pull requests
before merge" ([M1.1 §Acceptance criteria](../../specs/m0/M1.1-contract-validation.md))
is therefore **unenforceable** today. It can be observed, not compelled.
Changing branch protection or a ruleset is a shared-state write and is kept
outside this design's automatic scope.

### 1.6 Fixture inventory is complete

`contracts/json-schema/v1/` holds 5 schemas;
`contracts/fixtures/v1/` holds 5 `.valid.json` + 5 `.invalid.json`. The
inventory check at [validate-contracts.mjs:102-135](../../../scripts/validate-contracts.mjs#L102)
pairs them by stem. The 5 negative fixtures are all genuinely rejected (verified
in the CI log: `...invalid.json passed test` for each of the 5).

### 1.7 Ajv CLI argument shape, verified by probe

Two constraints discovered while designing §3.3, both measured against the
pinned `ajv-cli@5.0.0`:

- `--valid` and `--invalid` in the **same** invocation is rejected:
  `error: parameter -- must match exactly one schema in oneOf`. Positive and
  negative assertions must stay in **separate** calls (as today).
- `-r <schema>` for a schema already loaded via `-s` fails on duplicate `$id`:
  `schema with key or id "...event-envelope.schema.json" already exists`.
  Registering the whole `contracts/json-schema/v1/*.schema.json` set is
  therefore **not** a drop-in hardening.

This matters because the 5 root schemas cross-reference nothing (grep for
`$ref` in `contracts/json-schema/v1/*.schema.json` returns zero hits), so today's
per-schema `compile` + `test` calls are already sufficient. **No Ajv argument
shape changes are in scope.** Recorded so a later attempt does not re-derive it.

## 2. Decisions taken in this design

Approved by the owner during brainstorming; recorded so implementation cannot
silently re-litigate them.

| # | Decision | Consequence |
|---|---|---|
| D1 | **Zero-warning is the bar.** `M1.1` closes only when both lints report no findings at all. | The runner must fail on findings, and findings must be fixed at source. No suppression. |
| D2 | **Fix sources, don't relabel severity.** No `--severity` flag, no per-rule demotion. | OpenAPI gains 4xx responses + tag descriptions; `redocly.yaml` gets restructured. |
| D3 | **Transport: `npx-cli.js` through `process.execPath`** (option "W1"), no shell. | Windows local works; no `shell: true` argument-concatenation exposure; no DEP0190. |
| D4 | **Violation detection is proved in a scratch copy**, never by committing a broken contract. | A self-check job mutates a throwaway tree; `contracts/**` is never edited to prove CI can go red. |
| D5 | **`409` is the conflict class** for state/legal-transition errors. | Matches "Invalid transitions must return a stable conflict error" ([04-domain-model §transitions](../../specs/m0/04-domain-model-and-event-invariants.md)). |
| D6 | **M1.1 is next in the work queue**, ahead of the POC vertical slice. | Closing M1.1 unblocks POC-01; nothing else is folded in. |

## 3. Design

Four units, each independently checkable.

### 3.1 Unit A — `contracts/openapi/v1/openapi.yaml`: eliminate 31 findings

**A1. Eight tag descriptions (8 findings).** Every tag in the `tags:` block
(openapi.yaml:17-25: Health, Capabilities, Workspaces, Executors, Sessions,
Approvals, Questions, Artifacts) gets a `description` written **from the
existing M0 documents**, not invented. The owning source for each tag is
[03-api-session-event-protocol.md](../../specs/m0/03-api-session-event-protocol.md)
and [01-system-context-and-deployment.md](../../specs/m0/01-system-context-and-deployment.md).
Descriptions state what the resource is and who may call it; they must not claim
runtime existence (M0-08 §7 forbids that).

**A2. One 4xx per flagged operation (23 findings).** Grouped by what the
endpoint can actually do; every body references the already-declared
`ErrorResponse` schema (openapi.yaml:805-819) through a component, so no new
body shape is invented.

| Operations | Count | 4xx added | Justification |
|---|---:|---|---|
| `getLiveness`, `getReadiness` | 2 | `429` | Unauthenticated (`security: []`), so 401/403 would be fiction; overload/rate-limit shedding is real. `retryable: true`. |
| `getCapabilities`, `listModels`, `listTools` | 3 | `401`, `403` | Authenticated reads; scope filtering is real (`listExecutors`/`listModels` descriptions already say "visible to actor" / "Never returns credentials"). |
| `listWorkspaces`, `getWorkspace`, `listExecutors`, `listSessions`, `getSession`, `getSessionSnapshot`, `listSessionTasks`, `getSessionAudit`, `getArtifact` | 9 | `401`, `403`, `404` | Authenticated reads of identified resources; unknown id is the obvious case. |
| `createWorkspace`, `closeWorkspace`, `createSession`, `submitTurn`, `cancelRun`, `steerRun`, `resumeSession`, `decideApproval`, `answerQuestion` | 9 | `401`, `403`, `404`, `409` | All carry `IdempotencyKey`; conflict on illegal transition is mandated by D5. |
| `connectSessionEvents` | 1 | — (already 401/403) | Not flagged; untouched. |

Row counts: 2 + 3 + 9 + 9 = **23 flagged operations**, + 1 untouched = **24
operations total**. `getCapabilities` is an authenticated read but is grouped with
the discovery reads above for the 401/403-only treatment; it takes no `404` because
it addresses no identified resource.

`409` bodies use `error.code` from the stable table in A3. `retryable: true`
only where the same payload can succeed after the session advances (so
"already decided" is `retryable: false`, "session still running" is `true`).

**`422` is deliberately not added in this slice.** The linter requires only one
`4xx` per operation; introducing an unprocessable-entity class would need a
per-endpoint ruling on which bodies can be well-formed yet semantically invalid,
which is M1 implementation detail rather than a gap the validator found. Deferred.

**A3. A stable `error.code` enum.** `ErrorResponse.error.code` is currently an
unconstrained `{ type: string }` (openapi.yaml:815), which makes 23 hand-written
4xx blocks a drift farm. Add one component schema `ErrorCode` (enum) and constrain
`ErrorResponse.error.code` to it. Codes, each with the status that uses it:
`unauthenticated` (401), `forbidden` (403), `capability_denied` (403),
`not_found` (404), `state_conflict` (409), `session_not_active` (409),
`already_decided` (409), `not_awaiting_input` (409), `idempotency_mismatch` (409),
`rate_limited` (429).

This is a **tightening** of `ErrorResponse`, safe to do now and only now: Development
status shows no runtime implemented
([README.md](../../../README.md) "Development status"), so no consumer can break.
After the M1 freeze the same change would be breaking, which is why it belongs here
and not in the freeze.

`submitTurn` on a finished/archived session is **`session_not_active`** (409) per
D5 — a new session is created rather than resurrecting one; the contract does not
support resurrecting a completed session.

**A4. Coverage assertion, not lint, holds A2/A3 together.** Redocly cannot assert
"every `error.code` named in this document ∈ the enum". Add a runner check (§3.3,
C4) that parses `openapi.yaml` and asserts the set of code names used by 4xx
descriptions equals the `ErrorCode` enum, and that every operation under root
security declares at least one 4xx. If either side drifts, the gate goes red. This
is what makes the fix durable instead of a one-time cleanup.

### 3.2 Unit B — `redocly.yaml`: remove dead configuration

Today the four rule keys sit at top level and are reported as **unused** by the
AsyncAPI lint (§1.3). Redocly resolves rule sets per document API; a flat top
level applies OAS rules to an AsyncAPI run.

Change: split into API-scoped sections (`oas3_1:` / `asyncapi3:`) so each rule is
declared where it applies, and:

- `operation-4xx-response: error` (was `warn`) — D1/D2.
- `tag-description: error` (was inherited `warn` from `recommended`).
- `operation-summary: error` (unchanged; all ops already have summaries).
- `info-license` stays `off`, with its existing one-line reason.
- **Delete `operation-2xx-response: warn` and its WebSocket-101 comment.** Measured:
  the JSON problem list is exactly `{tag-description: 8, operation-4xx-response: 23}`
  — that rule produces **zero** findings today, including on `connectSessionEvents`
  (openapi.yaml:393), whose only success response is `'101'` (line 407). So the
  comment justifies an exemption for a case that does not occur. C2 fails on any
  finding at any severity, so a `warn` that never fires is dead weight; if a future
  contract adds a 2xx-less operation and the rule *does* fire, that is a real finding
  to fix, not a rule to demote.

The comment at `redocly.yaml` line 6 ("Add 4xx responses to operations as error
details are further formalized") is an unowned TODO inside a contract repo. It is
**deleted** and replaced by a reference to this design + A3, because A2 does the
work it deferred.

### 3.3 Unit C — `scripts/validate-contracts.mjs`: an honest gate

Five changes; no new abstractions.

- **C1 Transport (D3).** Replace the `npx.cmd` selection with `spawnSync(process.execPath, [npxCli, "--yes", ...args], { shell: false })`,
  where `npxCli` is resolved from `process.execPath` (`../lib/node_modules/npm/bin/npx-cli.js`)
  with a documented fallback search, and passed via `pathToFileURL` where needed.
  Capture `stdout`/`stderr` (`encoding: "utf8"`) instead of `stdio: "inherit"` so
  C2 can read them. If `npx-cli.js` cannot be located, **fail loudly** with the
  searched paths — never skip.
- **C2 Findings are failures (D1).** Run `redocly lint --format json`, parse the
  `problems` arrays, and fail if any problem of any severity exists. Redocly's own
  exit code is no longer the signal. Verified shape:
  `Object.values(j.problems).flat()` yields `{ruleId, severity, message,
  location[].source.ref, location[].start.line}`.
- **C3 Aggregate + count.** Keep `fail()` setting `process.exitCode = 1` (that
  behaviour is load-bearing, §1.4 retraction) **and** add a `checks` counter so the
  runner prints a final `PASS <n> / FAIL <m>` line. Use the returned booleans
  instead of discarding them at the 17 call sites.
- **C4 Coverage check (A4).** The `error.code` ⇔ `ErrorCode` enum assertion,
  plus: every operation under root security declares at least one 4xx.
- **C5 Keep the existing rules that already work.** The Markdown link walk (lines
  60-100) and fixture inventory (102-135) are correct and stay. The escaped-newline
  table-row guard (line 94, regex `\\n` followed by a pipe) stays — it exists because
  of commits `59d387e`, `81d2547`, `4e4270f` which were all "repair … line breaks".
  One sharp edge found while writing this document: that regex matches prose
  *describing* the guard, so any doc explaining it must break the character sequence
  up (as done here). C5 optionally narrows the guard to table rows only; it must not
  be deleted, because three commits exist precisely to repair what it catches.
- **Pin integrity.** `--package` names stay pinned (2.72.1 / 5.0.0 / 3.0.1). C1
  must preserve that: the resolved `npx-cli.js` gets the same `--package` args.
  Pinned versions are what make the `--format json` shape in C2 safe to depend on.

### 3.4 Unit D — the self-check that proves the gate has teeth

**Why a scratch copy.** The negative fixtures are part of the M1.1 inventory: the
inventory check fails if a fixture is *missing*
([validate-contracts.mjs:121-123](../../../scripts/validate-contracts.mjs#L121)),
and CI lints them green end to end. Committing a deliberately broken contract to
prove red would break every later PR and mask real drift. So: never mutate
`contracts/**`.

**New file: `scripts/selfcheck-contracts.sh`**, run by a second CI job
(`selfcheck`) that is **not** the required check:

1. `git archive HEAD | tar -x -C "$workdir"` — the same technique this design used
   to measure §1.4; it gives a pristine tree with no `.git` and no local edits.
2. Apply one of 5 deterministic mutations **inside `$workdir`**:
   (a) delete a tag `description`; (b) remove one operation's only 4xx block;
   (c) rename a required key in one positive fixture; (d) add a property absent
   from `additionalProperties: false` to a schema; (e) break a repository-relative
   Markdown link in `docs/specs/m0/README.md`.
3. For each mutation: run `node scripts/validate-contracts.mjs`, assert **exit
   ≠ 0** and that the `PASS <n> / FAIL <m>` line shows `m > 0`; print `M/K`.
4. Restore baseline between mutations; assert the baseline run exits 0 (proves the
   harness isn't failing for an unrelated reason).
5. Write `mutation self-check: <K>/<M> detected` to `$GITHUB_STEP_SUMMARY`.

**Naming (load-bearing).** Because a self-check job's green is *caused by the gate
going red*, it must never look like the real gate on a branch. Job name is
`Contract Validation (mutation self-check)`, exported from a single constant in
the workflow, and the real job keeps its current name. The runner also asserts the
required-check context if it can read it — but since `main` is unprotected (§1.5),
that assertion is informational until protection exists.

**Probes that must run before this job is trusted.** Two of these were already
answered by the measurements in §1 and are recorded as settled so the plan does not
re-derive them:

- P1 *(open)*: `--format json` on a document with a **fatal** error — exit code and
  whether `problems` still populates. Decides whether C2 must read both signals.
- P2 *(settled)*: a warnings-only document exits **0** with `problems` populated
  (§1.1, §1.2: 31 findings, exit 0). This is the exact hole C2 closes, so it needs
  no re-measurement — only a regression fixture in the self-check (mutation (a)).
- P3 *(open)*: `npx-cli.js` resolution on the CI runner image; the Linux install
  layout differs from Windows, so C1's path search must be proven there, not here.
- P4 *(partially settled)*: `git archive` works and was used for §1.4; what remains
  is proving `$workdir` is writable and `node` is on PATH in the self-check job.

## 4. Error handling and failure modes

| Failure | Behaviour | Why |
|---|---|---|
| `npx-cli.js` not found | Runner fails with every searched path printed. Never skips. | A skipped check is the §1.1 disease in a new costume. |
| `--format json` unparsable (tool crashed) | Fail, print the raw first 20 lines. | A crash is not a pass. |
| Redocly emits problems but exits 0 | **Fail** (C2). | This is precisely the bug being closed. |
| `npx` network fetch fails in CI | Fail; no retry loop. | Pinned packages + `npm` cache miss is a real supply-chain signal. |
| Self-check mutation *not* detected | Job goes red with `M/K` shown. | That is the acceptance criterion, not a flake. |
| A later dev adds a warning-level rule to `redocly.yaml` | C2 still fails on it. | Severity labels no longer gate; findings do. |

## 5. Testing

- **Unit-level (runner, local):** run the 5 mutations by hand on Linux **and**
  Windows after C1 lands; both must exit 1 with `FAIL ≥ 1`. This is the first real
  proof the Windows path works at all (§1.4).
- **Gate honesty:** the self-check job's `M/K` in the step summary.
- **Baseline:** the real `Validate` job green with `PASS <n> / FAIL 0`, and its log
  contains **no** `You have N warnings` line and **no** `[WARNING] Unused rules`.
- **Coverage:** C4 fails if a 4xx code is added to an operation without entering
  `ConflictCode`, and vice versa.
- **Clean-checkout rule** (standing memory: local green ≠ pushed commit builds):
  every acceptance run happens from `git archive`, never the dirty worktree.
