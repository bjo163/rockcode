# M1.4 — Structured Tool Calls and Bounded Runtime Orchestration

**Status:** Implementation submitted for CI review

## Provider-neutral contracts

- Tool definitions use stable names, descriptions and JSON Schema parameter objects.
- Tool calls carry provider-independent IDs, names and validated JSON argument strings.
- Assistant messages retain tool-call batches; tool results are correlated with their originating tool-call ID.
- Provider-specific function wire envelopes remain inside the provider adapter.

## OpenAI-compatible mapping

The adapter serializes tool definitions to the OpenAI-compatible tools array and sets tool_choice to auto. It parses assistant tool-call IDs, function names and JSON argument strings. Invalid, duplicated or incomplete call objects fail closed as provider gateway errors.

Assistant tool-call messages with empty content are encoded with JSON null content, and tool results include their originating tool_call_id and tool name.

## Runtime behavior

- One run is bounded to 1–16 model turns.
- Cancellation is checked between model turns and before each tool invocation.
- Tool execution requires an explicit ToolPolicy decision.
- Allow can invoke the registered ToolInvoker.
- ApprovalRequired emits tool.approval_required and returns WaitingApproval without executing the tool.
- If no policy or tool invoker is installed, approval is required by default.
- Deny returns a policy-denied tool result to the model and never invokes the tool.
- Every call in a response batch is authorized before any call in that batch is executed. If one call requires approval, the entire batch is held.
- Tool execution is reported through structured tool.started, tool.succeeded and tool.denied events.

## Explicit non-goals

- This slice does not expose filesystem, terminal or Git tools.
- No server route, UI, approval persistence or approval-resume API is wired yet.
- An allow decision is safe only when the caller injects a tool invoker that enforces workspace and sandbox boundaries.
- The local agent server still does not construct or expose a provider-backed run endpoint.
- Multi-agent task scheduling and session/event persistence remain separate milestones.

## CI acceptance

- Rust format, Clippy, workspace tests, architecture tests and strict cargo-deny on Ubuntu and Windows.
- Contract validation after documentation changes.
- Tests prove request mapping, tool-call parsing, bounded turns, batch approval, policy allow/deny and the default approval boundary.
